# AVTP 전송 계약 요구사항 대조 검토

2026-09-11. 대상: [전송 계약 v1](camera-avtp-transport-contract-v1.md).
결론: 방향은 요구사항과 일치하지만 아직 구현 기준으로 확정할 수 없다.
구독 프로토콜 중복은 제거되었으나, 영상 경로 연결의 미정 사항과 불필요한 정책 추가가 남아 있다.
이 검토는 로컬 코드와 참조 구현 문서 검토이며, 실기 시험 결과가 아니다.

## 1. 유지할 요구사항

- Pi→ZCU는 유지하고 ZCU→HPC의 실제 영상 데이터만 AVTP로 전환한다.
- 구독 여부·연결 수명은 기존 미들웨어가 관리한다. 별도 구독 갱신 메시지를 만들지 않는다.
- 사용자는 기존처럼 카메라 노드를 실행·종료한다. GUI 사용 절차도 유지한다.
- 서비스 상태는 기존 health 경로를 사용한다.
- JPEG 유지, HPC 유니캐스트, 기존 미들웨어 선택과 영상 전송 선택의 분리를 유지한다.
- 영상 조각의 길이 검증·재조립 상한·불완전 프레임 폐기는 필요한 전송 구현이다.

## 2. 수정 또는 보완이 필요한 사항

### R1. 실제 구독 지점과 AVTP 수신 연결이 아직 구체적이지 않음 — 우선 해결

[GUI nodes.yaml](../src/autosdv_gui_pkg/config/nodes.yaml)의 Camera 01~05는
`ethernet_image_publisher_node`를 실행한다. 이 [노드](../src/camera_perception_pkg/camera_perception_pkg/ethernet_image_publisher_node.py)는
실행 시 `/image_0N_raw`를 구독하고 디코딩 후 `/image_0N`을 발행한다.
YOLO의 GUI 설정도 camera_01을 dependency로 갖는다.

따라서 별도 최종 소비자 수요 판단을 추가할 이유가 없다. 카메라 노드가 실행되어
기존 미들웨어 구독이 존재하면 송신하고, 해당 구독이 사라지면 중지하는 동작을 보존한다.

현재 계약의 “AVTP 수신기→같은 raw 토픽에 재발행→기존 디코더”는 새 publisher와
기존 구독 endpoint가 섞이는 문제를 남긴다. 별도 수신 노드를 반드시 추가할 필요도 없다.
우선 기존 카메라 노드에 AVTP 입력을 연결하는 방식을 검토한다.
기존 미들웨어 subscriber는 발견용으로 유지하고, JPEG 데이터는 AVTP 수신 callback에서
기존 디코딩 함수에 넘기는 구성이 후보이다. 이 경우 raw 토픽의 데이터 관측 방식도
바뀌므로 로그·진단 등 기존 raw 토픽 소비자를 함께 추적해야 한다.
이 후보는 구현 확정안이 아니며 backend별 연결 검증 후 선택한다.

### R2. 미들웨어 기능은 있으나 AVTP 송신 제어에 연결된 상태는 아님

[Fast DDS publisher](../../S32G3_ZCU/src/backend/fastdds/image_publisher.cpp)와
[Cyclone DDS publisher](../../S32G3_ZCU/src/backend/cyclonedds/image_publisher.cpp)의
매칭 callback은 현재 로그만 남긴다. [camera_server](../../S32G3_ZCU/src/camera_module/camera_server.cpp)는
유효한 입력마다 publish를 호출하며 애플리케이션에서 매칭 수로 송신을 제한하지 않는다.
이는 미들웨어가 wire에서 실제로 얼마를 보낸다는 측정 결과와는 구분한다.

해야 할 작업은 기존 매칭 상태를 스레드 안전하게 AVTP 송신 조건으로 연결하는 것이다.
카메라별 초기 매칭 조회와 이후 변화, 중복 통지, 마지막 구독 해제, 재시작을 검증해야 한다.
ZCU 로컬 진단 subscriber가 HPC 구독으로 계산되지 않도록 endpoint 출처도 구분해야 한다.

[native Zenoh graph probe](../../S32G3_ZCU/src/backend/zenoh/graph_probe.cpp)는
현재 publisher 토큰을 추적하며 bridge 모드에는 같은 graph 추적을 적용하지 않는다.
구독 정보 전파를 backend별로 확인해야 하며, bridge의 존재를 실제 HPC 구독으로 대체하면 안 된다.
이 차이는 별도 애플리케이션 heartbeat를 만들 근거가 아니다.

### R3. 50 ms 고정 대기와 동기화 상실 시 중지는 사용자 요구보다 강함

계약은 영상이 먼저 도착해도 ZCU 입력 시각+50 ms까지 기다리게 한다.
사용자는 카메라 간 동시 표시나 일정한 재생 지연을 요구하지 않았다.
가능한 빠른 인식 입력이 목적이면 고정 대기는 불필요한 지연이 된다.

gPTP 활용과 동기화 상실 시 영상 중지는 별도 결정이다. 후자는 가용성 정책으로
확인이 필요하다. 동기화 없이 계속 전송하기로 결정하면 TV/TU 처리뿐 아니라 현재
timestamp 기반 재조립·메타데이터 결합·오래된 영상 판정도 함께 다시 설계해야 한다.
TV만 0으로 바꾸면 해결된다고 가정하지 않는다. 선택한 CVF 프로파일에서 가능한지 검증한다.

### R4. 프레임 ID 누락을 허용하면 기존 추적 동작이 바뀜 — 우선 해결

현재 입력 ID는 JPEG와 같은 입력 메시지에서 받아 이미지 header로 전달된다.
[차선 정보 노드](../src/camera_perception_pkg/camera_perception_pkg/lane_info_extractor_node.py)는
이를 `LaneInfo.frame_id`로 전달하며, 빈 값이나 파싱 실패는 0으로 바꾼다.

새 BEST_EFFORT frame_meta가 늦거나 손실됐다는 이유로 빈 ID를 내보내는 계약은
동일 영상을 처리했더라도 원본 프레임 추적을 잃게 한다. “예외가 발생하지 않음”은
기존 기능 보존과 같지 않다. header.stamp를 HPC 시각으로 바꾸는 것도 전송 변경과
별개의 의미 변경이므로 기존 stamp 사용처 확인 없이 확정하지 않는다.

원본 ID가 있는 프레임의 ID 보존을 기본 요구사항으로 유지한다.
사용자에게는 미들웨어로 작은 프레임 메타데이터를 운반해도 되는지만 질문한다.
허용되더라도 새로운 타입·토픽이 반드시 필요한 것은 아니므로 기존 헤더 전달 경로를
우선 검토한다. 메타데이터/영상 결합 key, 순서 변경, 손실 시 처리 및 유한 대기 상한은
별도 기술 검토가 필요하다. 원본 ID 없는 legacy 입력과 전송 중 ID 유실을 구분한다.

계약의 service_epoch는 AVTP 패킷 자체에는 없으므로 양쪽 데이터의 공통 key처럼
그대로 사용할 수 없다. 송신자 재시작 발견 및 시각 불연속 처리와 함께 결합 규칙을 확정해야 한다.

### R5. 정해 놓은 숫자가 현행 호환성·네트워크 근거와 연결되지 않음

VLAN 태그 필수와 PCP 5는 실제 SJA1110 설정을 확인하기 전의 선택이다.
기존 영상 큐를 유지할 수 있는 VLAN/분류 설정을 먼저 조사한다. VID와 MAC은 실기에서
확인할 값이며 사용자에게 임의의 숫자를 선택하게 할 사항이 아니다.

640×480·30 fps 및 JPEG subtype 제한은 입력 표본과 대조해야 한다.
legacy 4 B 입력 헤더에서 허용되던 JPEG 크기는 65,503 B인데 새 계약은 65,501 B로
축소한다. 입력 호환성을 줄일 근거가 없으므로 실제 입력 헤더 크기별 상한을 유지한다.
1400 B AVTPDU, 재조립 2개/64조각, 50/100/10 ms, watchdog 1초는 표준 의무가 아닌
프로젝트 정책값이다. 필요한 자원 상한은 유지하되 크기 산식과 기존 health 설정·실측에 맞춰 정한다.
버전·MAC·stream_id·길이 등 수신 필터와 시작 시 양단 설정 불일치 검출 방법도 구체화해야 한다.

### R6. 지원 라이브러리와 완료 판정이 아직 부족함

[Open1722](https://github.com/COVESA/Open1722)는 MJPEG를 지원 목록에 포함하지만,
[고정 revision의 CVF 예제](https://github.com/COVESA/Open1722/blob/dfb3e6bf27a560bd75c323d5608ab63568139d00/examples/cvf/README.md)는
H.264 전용이다. 헤더 API 제공과 JPEG 전체 packetizer 제공은 구분해야 한다.
표준 CVF/MJPEG 선택은 유지하되 실제 Pi JPEG 표본의 무재인코딩 왕복 검증을 선행한다.

현재 카메라 [Cyclone 설정](../src/launch_pkg/config/cyclonedds_image_01_participant20.xml)은
IVN 주소를 사용한다. “HPC 내부에만 발행”이라는 문장만으로 영상 본문의 IVN 재전송을
막을 수 없다. DDS/Zenoh/bridge별 실제 영상 경로와 발견 경로를 나누고 캡처로 확인해야 한다.
프레임 손실·지연의 전환 전 기준 측정, backend별 완료 범위, 기존 전송 모드 복귀 절차도
검증 계획에 명시해야 한다. 미들웨어 모드를 통째로 바꾸는 작업으로 범위를 넓히지 않는다.

## 3. 검토 당시 확인 질문 (아래 후속 지시로 갱신)

1. 영상은 완성 즉시 최대한 빨리 전달하는 것이 목표인지, 여러 카메라의 공통 시각 출력이 필요한지?
2. gPTP 동기화 상실 시 영상은 유지하고 시간 측정만 무효화할지, 영상을 중지할지?
3. 원본 프레임 ID 보존을 위해 이미지 헤더 등 작은 메타데이터는 미들웨어로 전달해도 되는지?

MAC/VLAN, 실제 JPEG 형식, backend API, raw 토픽 소비자와 frame_id/stamp 사용처는
에이전트가 확인할 기술 사항이다. 사용자에게 구현 세부 선택을 떠넘기지 않는다.
위 질문의 답변 전에는 관련 기존 계약 문장을 확정 요구사항으로 취급하지 않는다.

## 4. 사용자 후속 지시와 반영 결과

- 입력 즉시 전송·프레임 복원 즉시 처리는 기존 요구이다. 고정 50 ms 출력 대기를 제거했다.
- 동기화 상실 시 영상은 유지하고 동기화 기반 시간 측정만 무효화한다.
- 기존 frame ID는 AVTP 포맷으로 대체 가능할 때 제거한다.
- 새 frame_meta 메시지를 필수화한 결정은 철회했다. 다만 기존 ID는 Pi에서 CAN까지
  이어지는 원본 추적 번호이므로 8비트 AVTP packet sequence로 직접 대체할 수 없다.
- 비동기 CVF 재조립 및 기존 추적 ID의 동등한 대체 가능성은 기술 검토 항목이다.
  위 정책을 사용자에게 다시 선택하게 하지 않는다.

R1~R6은 검토 당시 발견 기록이다. 시간 정책과 frame_meta 필수화 관련 기존 문장보다
이 절과 갱신된 전송 계약을 우선한다. 코드·실기 설정은 변경하지 않았다.
